Fix the location synchronization bug in the current Instawork Research app.

BUG

When I click a city marker on the map, such as New York, and then click “View openings,” the page still displays sessions for Boston.

The map popup correctly shows:

New York
1234 openings

But the hero, available-sessions section, location selector, or session results continue using Boston.

Do not redesign the page. Diagnose and fix the underlying state and routing issue.

EXPECTED BEHAVIOR

When a user clicks “View openings” for New York:

1. The selected application location becomes New York.
2. The location selector displays “New York, NY.”
3. The sessions heading displays:
   “Available sessions near New York, NY”
4. The session list is filtered to New York.
5. The hero pay range is recalculated using New York sessions.
6. The URL reflects the selected market, when the app already supports location query parameters or routes.
7. Refreshing or navigating back should preserve New York rather than reverting immediately to Boston.
8. Boston must not remain visible anywhere unless Boston is actively selected.

ROOT-CAUSE INVESTIGATION

Inspect the current implementation and trace the full interaction:

- Map marker click
- Map popup state
- “View openings” click handler
- Selected city or selected market state
- Location selector state
- URL query parameters or route state
- Session filtering
- Hero pay calculation
- Any default-location initialization logic
- Any useEffect that resets the location to Boston

Look specifically for:

- Separate state variables for mapSelectedLocation and selectedLocation
- A popup that stores only a display label but not the market ID

- Incorrect city-to-market mapping

IMPLEMENTATION REQUIREMENTS

Use a single canonical selected-location object throughout the application.

It should contain the identifiers needed by the existing data model, for example:

{
  marketId,
  city,
  state,
  displayName,
  latitude,
  longitude
}

Do not rely only on the visible city label.

The “View openings” button must update the canonical location before scrolling or navigating.

For example, the flow should conceptually be:

handleViewOpenings(market) {
  setSelectedLocation(market)
  update URL or route if supported
  close popup
  filter sessions using market.marketId
  scroll to the sessions section
}

Adapt this to the existing framework and architecture rather than copying it blindly.

Do not create duplicate sources of truth.

If the URL is the source of truth, update the URL and derive selectedLocation from it.

If application state is the source of truth, ensure every component reads from the same state or context.

DEFAULT LOCATION LOGIC

Boston may be used only as an initial fallback when:

- no location exists in the URL
- no saved location exists
- no browser-derived location exists
- the user has not selected a location

Once the user selects New York, default initialization must not overwrite it.

If an initialization effect currently resets the location, add appropriate guards so it only runs when no valid user-selected location exists.

DATA FILTERING

Filter sessions using a stable market or location ID, not loose string matching when possible.

Confirm that New York map markers reference the same market identifier used by the New York session records.

Do not use the marker opening count as the selected location ID.
